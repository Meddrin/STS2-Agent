## Complete obtainable action ledger and two-layer evidence

> What this machine can obtain is **all action/decision entries persisted this round** and one `/strategy` during a run, not "all raw model conversation HTTP requests and responses". `/decisions` gives at most the latest 50 entries; the full action ledger is in the gitignored `build/live-2026-09-23/decisions.jsonl` (79 entries), and the run scope is also saved in `build/live-2026-09-23/sessions/*.json` (76 entries). Raw prompts, SSE deltas, Jev alternatives, and full provider responses are **not persisted in the current system**; a complete packet-by-packet audit of requests and results cannot be fabricated from these action records.

- 79 entries in total: **3** manual HTTP bootstrap entries, **54** regular model `agent_loop` entries, **22** Jev executions. 76 inside the run, matching the session record. The session also holds **84 chat entries**: 76 action displays and 8 completed assistant remarks; it has no raw per-turn `user/system/tool` messages and no full SSE, so these are not 84 complete provider requests. The eight remarks concern, respectively, two zero-energy end-turn-only situations, a map route evaluation, no energy after playing a card, a single-option map, the Inklet (墨宝) fight focus-fire/stripping slippery and viewing card rewards; the full text is stored only in the local isolated session and is not copied into this report. Jev appears only after entry 46; LLM actions before two-layer mode was enabled cannot be retroactively counted as Jev.
- Of Jev's 22 entries, `end_turn` 8, `play_card` 5, `choose_map_node` 3, `collect_rewards_and_proceed` 3, plus 1 each of card pick, rest, and continue. Every accepted Jev action has a request count of 1 and a confidence; this proves better than merely seeing the setting `dualLayerSoloEnabled=true` that **Jev really performed part of the actual operation**.
- During the run `/strategy` returned `dual_layer=true`, `jev_configured=true`, `strategy.source=llm`, the strategy update time, and `option_hints`. The session after exit has `strategy.source=llm`, update time about 23:56:25. The **old build deployed at the time** had `JevExecutionDecider.BuildRequest` pass the strategy `posture/instructions/option_hints`, the screen playbook, and the live compact state together to Jev; `StrategyPlanner.RefreshAsync` produces the macro strategy and does not operate the game directly. So there is **actual evidence for the plan→execute pipeline**, but the old build passed hints keyed by action type `play_card` straight through, while the options in the same Jev request are keyed by concrete IDs (such as `play_card:0->1`); hints that do not match the concrete alternatives are an interface defect confirmed by this round's code audit. The new build fixes the mapping offline and adds the macro goal, but the old run cannot be used to infer that "Jev acted according to the goal", and step-by-step quality still needs re-verification.
- Within the accepted action entries (not equal to total billing), the 54 `agent_loop` entries total at least **105 requests / 901,646 tokens**, and the 22 Jev entries total **22 requests / 88,451 tokens**. LLM planning requests reserve their cost outside the turn ledger, and failed requests/no-action fallbacks may also have produced no accepted action, so the above cannot be taken as the total actually billed by any provider. This cost shows that two-layer mode cannot yet be claimed as optimal in cost/speed; a comparison with the same situations, the same configuration, and a full request ledger is needed.

### The exact limits of Jev's consecutive `end_turn`

- Entries 61–65 (about 23:53:46 to 23:54:41) are consecutive Jev `end_turn`, with confidence about **0.36–0.52**; the `state_fingerprint` differs for all five actions, and afterward there are LLM and Jev `play_card` entries, continuing to the rewards screen. So these are **turns that really advanced under different game states**, not the same action replayed as is or a dead loop on a completely frozen screen.
- The low confidence is still worth investigating, but the old ledger **did not record per-step energy, hand playability, the alternatives list after Jev enumeration, the full Jev response, and did not keep historical strategy versions**. So it cannot be determined whether it "ended the turn early although cards were playable". The state after the previous action and the later screenshots also cannot stand in for these five specific decision moments. Neither can these five tactics be called correct, nor can the model be judged not to understand the game merely from consecutive `end_turn`.
- When two-layer quality is accepted again later, capture it with locally controlled **redacted per-turn evidence that by default contains no keys/full raw prompts**: screen/turn/energy, playable cards and targets, the option IDs given to Jev, the strategy revision number, Jev choice/confidence, the actual action result, and whether it fell back to the LLM; each trace aligned to the same decision ID. Ordinary game logs are not enough to reconstruct this evidence, and "optimized" cannot be claimed without having collected it.

1. The new layout, screenshot, and streaming-reasoning code must be rebuilt/deployed and re-verified **after closing the game**. For layout, it is best to first delete a non-primary model in the test settings, then view the settings and play pages separately; do not delete the real primary model configuration by mistake.
2. Reasoning output is shown only when the player has actively enabled "show reasoning content"; verify that increments appear **while the model is still generating**, that nothing is duplicated or crosses sessions on completion, and that nothing remains after unticking or pausing. A provider without `reasoning_content` should keep a normal conversation and not invent "reasoning" from nothing.
3. After Jev records the minimal redacted per-turn trace above, check on the same screens that the macro planning hints really map to concrete alternatives; if a card is playable in combat but it goes straight to `end_turn`, record hand/energy/strategy/confidence and then judge FAIL; without that evidence the result remains **quality pending verification**.
4. Two-layer quality evaluation must look at failure fallbacks, the share of accepted actions, total request/Token cost, and game progress together, not only at ticked boxes or the count of consecutive `end_turn`. The AI teammate was not verified this round and cannot be merged into "all P0 passed".
