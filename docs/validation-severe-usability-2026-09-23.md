# 2026-09-23 severe usability fixes: live validation plan

> **Historical snapshot: this is the original acceptance plan for the 2026-09-23 candidate, not a general operating procedure for the current version, and not a validation report.** The live results already executed that day, including the failures, are in [live-validation-2026-09-23-results.md](live-validation-2026-09-23-results.md); the "to be executed" wording below is the original plan's phrasing and does not mean no live operation had been done yet. The goal is to accept `154fcc6` of `dev` (together with the earlier `628ba75`), without requiring a run through three acts or spending a whole model session. The original candidate's offline build, 814 C# tests, 420 Python tests, and static gates had already passed; those results **cannot** replace in-game observation, and are not live acceptance of this round's later source fixes. Do not record rare scenarios that were not triggered as passed.

## 0. Boundaries, priorities, and stop conditions

- **P0 (required)**: isolated launch/mod identity, screenshot excludes the overlay, action availability during the map animation, single-player pause/queued actions, reward card pick hints, model card test and DeepSeek/Kimi thinking tool continuation turns, teammate exit and waiting for the human choice. An item can be judged passed only when the model and multiplayer preconditions are actually met; otherwise record *blocked* and the missing precondition.
- **P1 (conditionally triggered)**: skip with a re-roll relic, multiplayer potion whose target dies before the request, retryable 503 when an event spans an act, Jev's rest/reward/epoch/shop option filtering, non-standard tool-call shapes from local models. These depend on specific scenes/providers and can be collected during natural play; do not rewrite real saves to manufacture rare situations.
- **P2 (regression sweep)**: custom MCP address, model error display, long multiplayer status line, UI screen names, `build-mod.sh --skip-install` (a POSIX offline item, not counted as a Windows live item), `start-game-session.ps1` refusing to start when the old port is not released (a scenario for another controlled process; do not kill the player's existing game to test it).
- On an unexpected real save write, the wrong character being operated, a lost action response or unclear state, abnormal model billing, a game crash, or a teammate that cannot exit: **pause auto-play first, stop sending actions, and save the evidence**; do not replay `/action` automatically. A failing P0/P1 must be fixed and the related cases rerun; it cannot be merged to `main` with it.
- All paid calls use a test-only low budget/request cap, and the operator confirms the account quota and whether the real Jev/LLM may be used. Offline LLM compatibility unit tests cannot prove a provider's online protocol. For sensitive evidence keep only redacted summaries; do not store API keys, full request bodies, tokens, saves, or raw screenshots containing private data in the repository.

## 1. Preparation: isolation, deployment, baseline

1. Confirm `git rev-parse --short HEAD` matches the target, and record the working tree status in the report. Read the `STS2AIAgent/mod_manifest.json` version (`0.15.0` for this candidate); use the SHA256 of the DLL deployed after the build and the `/health` `mod_version`, `instance_role`, and port to confirm that **the new build is under test, not the old DLL**.
2. **Let the existing game close normally first**; `scripts/start-game-session.ps1` force-kills all `SlayTheSpire2` processes by default, so do not run it directly while the player is playing. `build-mod.ps1` copies the DLL/PCK to the game mods directory; first check the target install path and back up old files (if needed), to avoid a wrong version caused by a Workshop mod and a local mod with the same name. Deploy:
   ```powershell
   powershell -ExecutionPolicy Bypass -File scripts/build-mod.ps1 -Configuration Release
   ```
3. Use a **new clientId** different from the official Steam profile, and give the agent settings a separate path. The commands are examples only, adjust them to the local paths; `-ExtraArguments` is currently split on spaces and does not support a single quoted argument containing spaces. The launch script prepares `settings.save` for the isolated clientId and pins the specified API port; do not start a test run with debug actions using a real Steam account.
   ```powershell
   $env:STS2_AGENT_SETTINGS_PATH = (Join-Path (Resolve-Path .).Path 'build/live-2026-09-23/agent-settings.json')
   New-Item -ItemType Directory -Force (Split-Path $env:STS2_AGENT_SETTINGS_PATH) | Out-Null
   powershell -ExecutionPolicy Bypass -File scripts/start-game-session.ps1 `
     -ApiPort 18080 -Attempts 240 -DelaySeconds 1 `
     -ExtraArguments '--windowed --force-steam off --clientId 2026092301'
   $base = 'http://127.0.0.1:18080'
   $h = (Invoke-RestMethod "$base/health" -TimeoutSec 5).data
   $h | Select-Object mod_version,game_version,instance_role,play_phase,stop_kind,companion
   ```
   Add `-EnableDebugActions` only for stages that really need controlled event/modal triggers, and start a **separate test run**; keep debug actions off in the default stages. Do not put test keys in scripts or logs.
4. Record the file list/digests of the official Steam profile (to claim "official saves were not affected", the same list must be compared before and after), and confirm the isolated directory/settings path is not the official profile. Create the local evidence directory `build/live-2026-09-23/` (`build/` is ignored), and record the time, commit, game version, mod version, DLL SHA256, port, process PID, model name (not the key), and usage cap; for multiple instances, record the host/companion PID, port, and role separately. Do not commit full settings, session JSON, or sensitive responses.
5. Smoke test: `python scripts/run_sts2_validation.py mod-load`, `state-summary`, `state-invariants`, then read `/health` and `/state`. `/health.status` is normal, no reflection compatibility item is missing, and the state screen is reasonable; the initial `/state` and `/actions/available` do not contradict each other. On failure stop, and first check whether the mod is enabled and whether the port is held by an old process.

## 2. Execution matrix (grouped by precondition scene, to avoid aimlessly playing a full run)

For each item record **before** (screen, run_id, relevant lists and available actions), **operation** (UI/API and parameters), **response** (HTTP, `status`, `stable`, or error code), **after** (new `/state` and `/health`), the number of model requests used, and the verdict. Read `/state` before executing an action; `pending` is not a failure, wait for the state to stabilize and read again, and **when the response is unclear, only read state and do not resend the action**.

| --- | --- | --- |
| A1 P0 screen name/screenshot | Main menu or combat with the overlay shown; record the UI screen text and `/state.screen`. Call `GET /vision/screenshot`, save a local JPEG, and **inspect it manually**. | HTTP 200, valid JPEG, consistent screen name and no obvious UI stutter; the screenshot contains the game picture and **not the overlay**; the overlay recovers normally after the screenshot. If the screenshot route waits in a loop, record the duration and stop testing. |

Whenever reproducibility is insufficient, record the exact observation boundary and support it with existing contract/unit tests; never write "did not reproduce" as a live pass.

## 3. Regression, wrap-up, and report format

- Before and after each stage run the read-only `/health` and `/state`, and keep one focused summary (screen, run_id, `available_actions`, play_phase, stop_kind, request/Token counts, companion PID). Redact UI screenshots locally. `GET /vision/screenshot` is itself the screenshot test and must not be used to verify whether the overlay is visible (it hides the overlay by design); overlay recovery must be checked by looking directly at the game window.
- At the end of a stage first send `{"running":false}` with `POST /session/control` and confirm the pause; for dual launch, first close the host from the UI/normally and then confirm the companion exits. Only **the controlled crash path of A9** may use `Stop-Process -Id <pid> -Force` on the recorded test PIDs; never kill everything by mistake with `Get-Process SlayTheSpire2 | Stop-Process`.
- If you claim the official profile was untouched, repeat the same official Steam profile list/digest and compare; isolated saves may change from play, which is expected. Keep the local evidence in `build/live-2026-09-23/`; do not commit `*.save`, settings, `sessions/`, keys, or raw screenshots with private data.
- If debug actions are used, list "debug-synthesized" and "natural play" evidence separately, and do not treat `inject_event_churn` as proof of natural action/screen transitions. The screenshot in the previous round's [live-validation-checklist.md](live-validation-checklist.md) **contained** the overlay, so this round's A1 must take a new image and cannot reuse the old evidence.

Suggested fields to fill in per item in the report:

```text
Environment: date/commit/game version/mod version/DLL SHA256/isolated clientId/host port/companion port (keys not recorded)
ID: A1…A13
Status: PASS | FAIL | BLOCKED | NOT_RUN
Precondition: screen, run_id, key flags, model and budget cap
Operation and time: UI or API, and where needed HTTP code, status, stable, error.code, retryable
Before/after: key state/health differences, request and Token increments, the matching local evidence file names
Verdict: which criterion in this table it matches or does not match; repro steps of a failure and the time of the first anomaly
```

Only after the applicable P0 items are complete, every P1 item has an explicit PASS or a reason it could not be triggered, and there is no regression/save contamination, may a "candidate can be merged" recommendation be given for the `dev → main` PR; key P0 items not executed or blocked must be listed explicitly as acceptance gaps and cannot be replaced by offline results.
