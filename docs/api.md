# STS2 AI Agent Mod - HTTP API

Status: implementable
Protocol version: `2026-03-11-v1`

---

## Constraints

- The protocol is based on `HTTP + JSON`
- Default listen address: `http://127.0.0.1:8080`
- The response type is fixed to `application/json; charset=utf-8`
- New fields must be backward compatible; existing fields are never removed
- Machine-readable OpenAPI 3.1 / JSON Schema: [`openapi.json`](openapi.json). It is generated by `scripts/api_schema.py` from the Router routes, the C# wire payload records and the validated shared vocabulary on this page. Do not edit it by hand; after a change, run `python scripts/api_schema.py`. `python scripts/check_verification_gates.py --only api-schema` rejects a stale artifact byte for byte.

---

## Common response format

**On the wire the JSON is compact**: the response body has no indentation or spaces (`{"ok":true,...}`); the examples in this document are expanded only for readability.
This is not a matter of style. If you strip the indentation from every real response example in this document, **35.6% of the bytes are formatting**
(44% for the most deeply nested combat state), and the readers of these responses are parsers: the MCP sidecar, external agents, verification scripts. For an agent these bytes are tokens paid on every
decision. To read them by eye, pipe the output through `jq .` yourself:

```bash
curl -s http://127.0.0.1:8080/state | jq .
```

Field names are still PascalCase; this is part of the contract (pinned by `JsonHelperTests`).

### Success

```json
{
  "ok": true,
  "request_id": "req_20260310_120000_1234",
  "data": { ... }
}
```

### Failure

```json
{
  "ok": false,
  "request_id": "req_20260310_120000_1234",
  "error": {
    "code": "invalid_action",
    "message": "Action is not available in the current state.",
    "details": { "action": "end_turn", "screen": "MAP" },
    "retryable": false
  }
}
```

## Error codes

| Error code | HTTP status | Meaning | Retryable |
| --- | --- | --- | --- |
| `invalid_request` | 400 | The request body is missing a required field or is malformed | No |
| `not_found` | 404 | The route does not exist | No |
| `invalid_action` | 409 | The action cannot be executed in the current state | No |
| `invalid_target` | 409 | The target index is out of range | No |
| `action_in_flight` | 409 | An action is already executing (including the state transition it is waiting for). This request was **neither executed nor queued**: wait for the previous action's response, read `/state` again, then retry. The details carry `in_flight_action`, the name of the action holding the slot | Yes |
| `state_unavailable` | 503 | The game state cannot be read safely right now (for example during a transition) | Yes |
| `unavailable` | 503 | The instance hosting the two-layer strategy surface (`GET`/`POST /strategy`, MCP tools `get_planner_briefing`/`update_play_strategy`) has no strategy store bound (for example an offline test environment). Does not occur on a normal in-game instance | Yes |
| `forbidden_actor` | 403 | In multiplayer, an attempt to perform an action for another character | No |
| `mcp_disabled` | 403 | /mcp was requested but native MCP is not enabled | No |
| `screenshot_unavailable` | 409 | The game viewport cannot be captured yet | Yes |
| `session_not_ready` | 409 | The session is not ready yet (for example team setup is not finished) | Yes |
| `pause_pending` | 409 | The pause has not completed yet; retry shortly | Yes |
| `internal_error` | 500 | Internal service exception | No |
| `listener_error` | 500 | The HTTP listener loop itself threw (not the failure of a single route handler). The connection may no longer be healthy, so confirm with `GET /health` that the service is still up before retrying | Yes |
| `local_only` | 403 | This endpoint only accepts requests from the local machine (loopback) | No |
| `companion_session_required` | 403 | A valid AI teammate session token is required (see below) | No |
| `companion_not_ready` | 409 | The teammate instance is not ready yet and cannot respond to control | Yes |
| `not_host` | 409 | `POST /teammate/control`, which belongs to the main window only, was called on a `companion` instance | No |
| `teammate_control_failed` | 409 | `POST /teammate/control` could not confirm the teammate's start / pause: no team is formed yet, the teammate process has exited, the previous control has not finished, or the teammate did not confirm. The failure reason is in `error.message` | Yes |
| `invite_failed` | 409 | Inviting the AI teammate failed (the main menu state or the configuration does not qualify) | Yes |
| `continue_failed` | 409 | Failure **after** the load-save room flow has started (the load screen did not open, or the local direct-connect port 33771 is still held by the previous run; retry after restarting the game). Unmet preconditions (not the host's main menu, this is the teammate instance, the local character is auto-playing, there is no multiplayer save) still return `invalid_action`; if a dual launch is already in progress it returns 200 `pending` instead, consistent with a concurrent `invite_ai_teammate`. An unverified play model does **not** block `continue_ai_teammate`: as with the invite, `requireVerifiedPlayModel` and `ReadyToInvite` take two separate routes, so when unverified the teammate is still launched, it just does not auto-play | Yes |
| `invalid_action` (the NetId precheck of `continue_ai_teammate`) | 409 | The read-only comparison **before** loading the save failed: the local NetId is not in the multiplayer save's `players[].net_id` (the game would reject the load, rename this run's save to `*.VAL.corrupt`, move it away and not restore it), or the NetId of the AI teammate to be launched is not in the save (joining would be rejected with `NotInSaveGame`). The details carry `save_player_net_ids`, plus `local_player_id` or `companion_client_id` | No |
| `invalid_action` (the command of `run_console_command` threw) | 409 | The game accepted the command but the implementation threw (for example `bestiary` throws `NullReferenceException`). The message is `Console command failed: <exception type>: <exception message>`, and the details carry `command` | No |
| `collection_not_found` | 404 | The collection name of `GET /data/{collection}` does not exist | No |
| `export_error` | 500 | Exporting the game metadata failed | Yes |
| `origin_not_allowed` | 403 | The `Origin` of the native MCP request is not trusted | No |
| `method_not_allowed` | 405 | `/mcp` was requested with a method other than POST. Native MCP uses Streamable HTTP and only accepts JSON-RPC over POST | No |
| `payload_too_large` | 413 | The `/mcp` request body exceeds 1 MB | No |
| `unknown_tool` | 404 | The `name` of a native MCP `tools/call` is not a tool registered on this surface (the Python sidecar and the native surface share one set of tool names). The message carries the tool name and `tools/list` gives the current list; this is a typo by the caller, not a failure that can be retried | No |

The pause menu that appears after a human presses pause, and the Settings page and the Compendium pages entered from it (card overview, relic collection, potion lab, bestiary, character stats, run history), are all hosted by the same `NCapstoneSubmenuStack` container. `screen` reports the name of the page on top of the container stack (`PAUSE_MENU`, `SETTINGS`, `COMPENDIUM`, `CARD_LIBRARY`, `RELIC_COLLECTION`, `POTION_LAB`, `BESTIARY`, `STATS`, `RUN_HISTORY`), not the room those pages cover; an unknown page in the container still falls back to `CAPSTONE_SELECTION`.

These are all manual menus, and the room actions swallowed by the pause no longer appear: `end_turn`, `play_card`, `choose_map_node`, `resolve_rewards` and `save_and_quit` are never advertised, and calling them directly returns 409 `invalid_action`. `capstone` does not appear either: the buttons in the container are navigation tiles, filter checkboxes and control hit areas (`Hitbox`), not an agent option list, so `choose_capstone_option` is neither advertised nor callable.

Apart from the pause menu itself, each of these pages keeps one action: `close_main_menu_submenu` goes back one level (equivalent to the page's own back button `Stack.Pop()`), for example `CARD_LIBRARY` -> `COMPENDIUM` -> `PAUSE_MENU`. It stops at the pause menu, and that page offers no action at all: resuming the game is up to the human, and the agent does not click "Resume" for them. `close_cards_view` is not usable on these pages: a container page is not a card-view screen, and its jurisdiction covers only the card-view screens and piles in combat plus the `CARD_INSPECT` / `RELIC_INSPECT` overlays (see the action table below).

## Action Status

The `status` field after an action executes:

| Value | Meaning |
| --- | --- |
| `completed` | The action is complete and the returned `state` has settled |
| `pending` | The action was submitted but the game state is still in transition (waiting for animations / the queue to drain) |
| `failed` | The action was executed but failed; `mcp_server/src/sts2_mcp/client.py` raises `action_failed` when it reads this value, so it must not be treated as success |

## `GET /health`

Returns the basic Mod status, this session's run counters and the auto-play state. Use it to confirm the game is running and the Mod is loaded; whether auto-play is running and why it last stopped are also read here.

### Response example

```json
{
  "ok": true,
  "request_id": "req_20260911_121549_7955_4",
  "data": {
    "service": "sts2-ai-agent",
    "mod_version": "0.16.2",
    "protocol_version": "2026-03-11-v1",
    "game_version": "v0.111.0",
    "status": "ready",
    "api_host": "127.0.0.1",
    "api_port": 8080,
    "process_id": 50708,
    "instance_role": "human",
    "mcp_enabled": false,
    "mcp_url": null,
    "play_running": false,
    "play_phase": "paused",
    "stop_kind": null,
    "session_requests": 12,
    "companion_process_alive": false,
    "companion_process_exited": false,
    "companion": null,
    "dual_status": "No second game instance is running.",
    "dual_launch_outcome": null,
    "team_control_status": "Teammate control is not connected yet."
  }
}
```

### Field description

| Field | Type | Description |
| --- | --- | --- |
| `service` | string | Fixed to `sts2-ai-agent`, used to confirm the responder is really this Mod and not another service on the same port |
| `mod_version` | string | Mod version, identical to the `ModVersion` constant in `STS2AIAgent/Server/Router.cs` |
| `protocol_version` | string | HTTP protocol version |
| `game_version` | string | Game version; the example value changes with game updates |
| `status` | string | `ready`: the Mod can still read all internal state of this game version. `degraded`: at least one game-private member reflected by name can no longer be found. Requests are still served, but the affected fields fall back to defaults, and **`compatibility` says exactly which are missing**. This value is derived from the startup self-check, not hardcoded |
| `api_host` / `api_port` | string / integer | The HTTP API address of **this instance** itself. When the port is taken it is incremented automatically, so do not hardcode 8080; trust the value here |
| `process_id` | integer | Game process PID, used to verify the identity of dual-launch windows |
| `instance_role` | string | `human` (the player window) or `companion` (the AI teammate instance) |
| `mcp_enabled` / `mcp_url` | boolean / string\|null | Whether in-process MCP is enabled and, when it is, its address |
| `play_running` | boolean | Whether auto-play is running |
| `play_phase` | string | Auto-play phase, common values `running` / `paused` / `stopping` |
| `stop_kind` | string\|null | The category of the last auto-play stop; `null` if it never stopped |
| `session_requests` | integer | Number of model requests used in this session (can be reset by "Reset session statistics") |
| `companion_process_alive` / `companion_process_exited` | boolean\|null | **Meaningful on the host only.** The main window reports whether the AI teammate process is running / has exited; with `instance_role=companion` both are `null` (not applicable), so the companion is not described as still having another teammate process to manage |
| `companion` | object\|null | **Meaningful on the host only.** Present when this is the main window and the teammate process of the current team is still running (back to `null` after the teammate exits). `api_host` / `api_port` / `process_id` are the teammate instance's HTTP API, used to program directly against the teammate's `GET /state` and `POST /action`; `auto_play` says whether this team runs on AI self-play (`true`) or external control (`false`). The teammate session token **never** appears in any response; the companion itself is always `null` |
| `dual_status` / `team_control_status` | string\|null | **Meaningful on the host only.** The main window returns the human-readable status of the dual launch and of teammate control; the companion returns `null` and does not fabricate the host defaults "dual launch not started" or "not connected" |
| `dual_launch_outcome` | string\|null | **Meaningful on the host only.** The structured result of the dual launch, for external clients to classify success or failure; do **not** use the `dual_status` text. `null` if the host has not attempted yet or the role is companion; otherwise `InProgress` / `Succeeded` / `Failed` / `Rejected` / `Canceled` (the `DualLaunchOutcome` enum names, without `Idle`) |
| `compatibility` | object | The result of a one-time self-check, at startup, of the game-private members the Mod depends on. `reflected_members_checked` is the total number of members checked, `reflected_members_missing` is how many could not be found, and `missing_members[]` gives, per entry, `member` (`Type.Member`) and `feature` (the feature that broke). After a game update the most common way the Mod breaks is that a private field is renamed, and reads then silently fall back to defaults; this block is the only signal |
| `state_build` | object | Time spent building the state payload, counting only the build itself and not waiting for the game thread. `/state`, every action response and every SSE refresh builds it once, and all of them run on the game thread: the game renders no frames during a build. `slow_threshold_ms` (100, roughly a 6-frame hitch at 60 fps), `samples`, `slow_builds`, `last_ms`, `max_ms` with its `max_screen`, and `recent_p50_ms` / `recent_p95_ms` over the most recent `recent_samples` (at most 256) builds; the timing fields are `null` while there are no samples. A build over the threshold logs a `WARN` in the game log, at most one every 30 seconds, noting how many were suppressed in between |

### `stop_kind` values

| Value | Meaning |
| --- | --- |
| `null` | This auto-play run did not end with a stop (still running, or not started yet) |
| `budget` | Hit the session budget or the request count limit |
| `run_end` | Left the current run, or the run identifier changed |
| `config` | Model configuration or authentication problem (401/402/403/404/422, invalid key and so on) |
| `network` | Network or timeout problem (408/429/5xx, connection refused and so on) |
| `failed` | Any other reason, including 3 consecutive failed decisions |

### `session` object

**This is the first basis for routing**; do not infer singleplayer / multiplayer from the screen name or the tool name. `/state` always carries `session`, including on the main menu.

| Field | Type | Description |
| --- | --- | --- |
| `mode` | string | `singleplayer` or `multiplayer` |
| `phase` | string | `menu` / `character_select` / `multiplayer_lobby` / `run` |
| `control_scope` | string | Whom this instance can decide for. Currently always `local_player`: even in a multiplayer run, it only operates its own character |

`mode` is always reported as `singleplayer` in the main menu phase (there is no connection yet); after entering character select or a run it is decided by that screen's own
`NetService.Type`.

### `multiplayer` object

The in-run multiplayer connection summary. A singleplayer run carries it too (`is_multiplayer = false`); in the lobby phase, look at `multiplayer_lobby` instead.

| Field | Type | Description |
| --- | --- | --- |
| `is_multiplayer` | boolean | Whether this run is a multiplayer run |
| `net_game_type` | string | The game's own connection type name |
| `local_player_id` | string \| null | Local player id, in the same space as `combat.players[].player_id` |
| `player_count` | number | Current player count |
| `connected_player_ids` | string[] | List of the ids of connected players |

`combat.players[]` / `run.players[]` and `target_index` **share the same index space**: for an
action that takes effect on the N-th player, `target_index` is that player's position in these two arrays, not the `player_id`.

### `combat` object

#### `combat` top-level fields

| Field | Type | Description |
| --- | --- | --- |
| `action_readiness` | object | Whether the executor accepts combat actions at this moment and, if not, which step it is stuck at. See below |
| `player` | object | The local player's combat state |
| `players` | object[] | Combat health lines of all players in this run (including the local player). In multiplayer, used to decide whether a teammate needs rescue; a singleplayer run has only one entry |
| `hand` | object[] | The local player's hand |
| `enemies` | object[] | Enemies on the field |
| `end_turn_will_kill_player` | boolean | Whether ending the turn right now would kill the local player; it includes enemy intents **and** damage over time such as poison / constrict that resolves before you can act again, with the entry-by-entry basis in `lethal_risks` |

#### `combat.action_readiness`

In one `/state` response, `available_actions`, `combat.action_readiness` and the potion usability flags **come from the same gate evaluation**
(since v0.12.4). The gate has a 200ms stable sampling window; it used to be re-evaluated per action, so one response could straddle the sampling window and contradict itself.
So now: a snapshot with `can_use_combat_actions = true` necessarily carries `play_card` / `end_turn` too, and vice versa. **Do not treat these
two as independent signals to cross-check**; they are two projections of the same conclusion.

`reason` values (listed in the gate's evaluation order, first match returns; only when nothing matches is it `ready`):

| Value | Meaning |
| --- | --- |
| `modal_open` | A blocking popup is covering; `confirm_modal` first |
| `combat_screen_unavailable` | Not on the combat screen, or the combat state is empty |
| `combat_not_in_progress` | Combat has not started |
| `combat_over_or_ending` | Combat is over or wrapping up |

| `player_actions_disabled` | The combat manager has temporarily disabled player input |
| `combat_room_not_active` | The combat room is not in active mode |
| `hand_unavailable` | The hand node is unreadable |
| `hand_in_card_play` | The previous card's play animation has not finished |
| `hand_in_card_selection` | The hand is in selection mode (for example a discard or exhaust choice) |

| `game_action_queued` | A GameAction in the queue is ready |
| `action_queue_unsettled` | The queue reports an action still in flight |

#### `combat.lethal_risks[]`

The entry-by-entry basis of `end_turn_will_kill_player`. An empty array when there is no risk.

| Field | Type | Description |
| --- | --- | --- |
| `risk_id` | string | Risk identifier |
| `source` | string | Risk source (enemy intent / own Power and so on) |
| `will_kill_player` | boolean | Whether this entry alone is enough to kill |
| `reason` | string | Explanation of the judgment |
| `incoming_damage` | number \| null | Incoming damage |
| `damage_after_block` | number \| null | Damage after block is subtracted |
| `player_hp` | number \| null | Player HP at resolution time |
| `player_block` | number \| null | Player block at resolution time |
| `power_id` | string \| null | ID of the source Power (when the source is a Power) |
| `power_amount` | number \| null | Stack count of that Power |

These `risk_id` values currently occur:

| `risk_id` | Trigger condition | Key point |
| --- | --- | --- |
| `incoming_damage` | Total enemy intent damage after subtracting current block is >= current HP | Intent only, no damage over time |
| `poison_next_turn` | The total poison resolved **at the start of your next turn** is >= current HP | Ignores block (`damage_after_block` equals `incoming_damage`) and resolves before you can play cards again, so ending the combat this turn avoids it |
| `constrict_turn_end` | The damage constrict deals **at the end of this turn**, after block, is >= current HP | Can be blocked, so `damage_after_block` and `incoming_damage` often differ |
| `doom_turn_end` | Doom stacks >= current HP | Kills outright at the end of your turn, block does not take part in the comparison; `incoming_damage` is empty because it is not a hit of damage |
| `magic_bomb_turn_end` | The damage Magic Bomb deals after the end of your turn is >= current HP | Ignores block. A bomb the player plays themselves hits enemies and does not enter this table |
| `sandpit_countdown` | Sandpit countdown <= 1 | Ending the turn counts as lethal, unless the Boss is killed first or the countdown was already raised with Frantic Escape |

In other words, this field covers all the damage that will land "after the turn ends and before you can act again", not just enemy intents.
Poison used to be the main source of "marked safe, then died at resolution".

| Field | Type | Description |
| --- | --- | --- |

#### Redundant keys removed from compact in v11

When `agent_view.version` went up to **11**, three "second ways of writing the same data" were deleted. They were all just redundancy
and carried no unique information; removing them saves a good chunk of tokens on every `get_game_state`:

| Removed | Original content | Use instead |
| --- | --- | --- |
| top-level `actions` | A duplicate array **identical word for word** to `available_actions` | `available_actions` |
| top-level `profiles` | A static table that was always `[{id:1},{id:2},{id:3}]` | `native_profile_id` (used by `switch_profile`) |
| `combat.draw_cards[]` / `discard_cards[]` / `exhaust_cards[]`, `run.piles.*_cards[]` | A **second pile view** from the same source as `draw[]` / `discard[]` / `exhaust[]` (one object per card) | The grouped lines (`line` + `card_ids`) of `combat.draw[]` / `combat.discard[]` / `combat.exhaust[]` / `run.piles.*` |

**Not one** `/state` field changed. The above happens only in this derived compact view, which already has a version number.

## `GET /decision-snapshot`

The readings needed for one decision, taken from **one** game-thread state build: the compact state and the action descriptors are two projections of the same walk over the action surface.

`GET /state` and `GET /actions/available` are two requests, that is, two frames: the game advances between the two requests, so the state the caller just read and the action indexes read right after
may describe different moments, and index validation would check an action against a hand it has never seen. This route gives both halves in one state build, so reading it
leaves no such gap; the two endpoints above are kept as they were and can still be called separately when only one half is needed.

### Response fields

| Field | Type | Description |
| --- | --- | --- |
| `state` | object | The compact `agent_view` (same shape as the `agent_view` of `GET /state`); falls back to the full payload when that build produced no `agent_view` |
| `available_actions[]` | object[] | The action descriptors produced by the same walk, with fields exactly identical to the `actions[]` of `GET /actions/available` |

## `POST /action`

Executes a single game action.

Only one action may run at a time. All entry points (HTTP, native MCP, the in-game Agent, the teammate coordinator) converge on the same lease in

## `POST /session/control`

Starts or pauses auto-play of the **local character**. The "Start auto-play" button of the in-game overlay goes through the same entry point; scripts and acceptance flows use it instead of mouse clicks.

- Accepts loopback requests only; a non-local source returns 403 `local_only`
- Request body `{"running": true}` starts and `{"running": false}` pauses; a missing field or a non-boolean value returns 400 `invalid_request`
- On a `companion` instance it is equivalent to controlling that instance itself, see `/companion/control` below. `running: true` passes the same gate as the in-game "Resume play" and `POST /teammate/control`: when the play model is unverified it returns 409 `session_not_ready`, and the message is the "Test connection" prompt; `running: false` is always available, and pausing is not affected by the gate

### Response example

```json
{
  "ok": true,
```

## `GET /events/stream`

A server-push event stream, used to wait for state changes instead of polling `/state` repeatedly.

- `Content-Type: text/event-stream`, chunked transfer
 - Heartbeat: an SSE comment line (starting with `:`) is sent every 15 seconds, and the connection stays open
 - When the connection is established, a `: stream opened` comment line is sent first

### Frame format

A frame consists of four parts and ends with a blank line:

```
id: 897
event: combat_started
data: {
data:   "event_id": 897,
data:   "type": "combat_started",
data:   "timestamp_utc": "2026-09-11T12:45:53.9202914Z",
data:   "data": {
data:     "run_id": "C9LRZTK3L1B4",
data:     "turn": 1
data:   }
data: }

```

Note: the JSON is output over **multiple lines**, so one frame has several `data:` lines. Per the SSE spec, the client must join all `data:` lines with newlines and then parse the whole, and must not read only the first line. The `wait_for_event` in `mcp_server/src/sts2_mcp/client.py` handles it this way.

Frame content: `id:` is the event sequence number, `event:` is the event type, and `data:` is the full event envelope, containing `event_id`, `type`, `timestamp_utc` and the event-specific `data`. `event_id` increases monotonically within this process, but the server keeps no replay backlog.

Event polling runs on demand: with no subscribers, the full `/state` is not built periodically; the first subscriber wakes the single shared poll loop, and after the last subscriber leaves polling goes idle and drops the snapshot kept from the previous session. Therefore:

- When a connection is established and a snapshot already exists (within the same active session), it receives `stream_ready` **immediately**;
- If there is no snapshot yet (the first subscription, or the previous session ended with the last subscriber), the connection first receives the `session_started` produced by the first sample, and **right after** it receives the `stream_ready` of the same sample, in the fixed order `session_started` -> `stream_ready`.

Each client uses a bounded queue with capacity 256. When the queue is full the server **neither silently drops old events nor blocks the producer**; it completes and closes that slow client's stream. The client should reconnect and realign with the new `stream_ready` (or a fresh `/state`). `event_id` increases globally; the initial snapshots of other subscriptions also use numbers, so a single subscription does not guarantee contiguous numbering. A jump in numbering alone does not prove a broadcast event was lost, and the server provides no history replay; after reconnecting, read a new snapshot. The official Python `wait_for_event` reconnects within its original total deadline.

No duplicate frames are sent when the state has not changed: polling sends an event only when its payload differs from the last published one. `stream_ready` appears only at two moments, once when a connection is established (a snapshot exists) and once after the first sample of a session; polling itself only updates the snapshot and no longer broadcasts.

On process shutdown, polling stops first and then the subscribers are cleared, so no state from an old lifecycle is written as `stream_ready` after shutdown. After the last subscriber disconnects, the server only finds out at the next write failure (heartbeat interval 15 seconds, about 30 seconds for two heartbeats in the worst case); during this time the connection is still open in the TCP sense and so is still counted as a subscriber. Measured on a real game on 2026-09-20: polling stopped about 33 seconds after disconnect, and `samples` stopped growing afterwards. An RST / write failure (for example the reset produced when `curl` exits at once) is detected earlier.

Event types:

| Type | Trigger |
| --- | --- |
| `stream_ready` | Sent once right after the connection is established with the current state (`run_id`, `screen`, `in_combat`, `turn`, `action_window_open`), so a new client does not have to poll `/state` first |
| `session_started` | Session start |
| `screen_changed` | Screen switch |
| `combat_started` / `combat_ended` | Entering / leaving combat |
| `combat_turn_changed` | Combat turn change |
| `player_action_window_opened` / `player_action_window_closed` | The window in which the player can act opens / closes |
| `route_decision_required` | The map needs a route choice |
| `reward_decision_required` | A reward needs a choice |
| `event_state_changed` | Internal event state change |
| `available_actions_changed` | The set of available actions changed |
| `decision_made` | One **accepted** action was written to the decision log (the same record as `GET /decisions`). The payload is `id`, `source`, `action`, `reason`, `state_fingerprint`, `requests_spent`, `total_tokens`, `timestamp_utc`; rejected or failed actions do not emit this event |
| `debug_churn` | Published only by the debug action `inject_event_churn` (needs `STS2_ENABLE_DEBUG_ACTIONS=1`). The payload carries `synthetic: true` and an `index` starting at 1, used to fill a slow subscriber's queue on a real game |

**Event type names come from the `EventChurnPolicy.EventType` constant, not from a literal.** The gate's event name extraction only recognizes literals, so this is stated explicitly here: `debug_churn` is a name assembled from a variable and will not be discovered by automatic extraction. When adding any event name in **variable form**, update both this table and the extraction rule, or both will silently miss it.

Measured on an isolated copy on 2026-09-11: within a 45-second window it received `: stream opened`, 2 `: heartbeat` lines and 123 lines of frame content, with event types covering `stream_ready`, `screen_changed` (SHOP->COMBAT), `combat_started`, `player_action_window_opened`, `available_actions_changed`. Evidence: `build/validation-2026-09-11/sse-frames.jsonl` (gitignored).

## Two team-up routes

"Invite AI teammate" has two routes with different prerequisites. Which one is taken is decided by **whether the play model is verified** (in code, `FirstRunSetup.Evaluate(settings).ReadyToInvite`), and the caller needs no extra parameter.

| | AI self-play | External takeover |
| --- | --- | --- |
| Prerequisites | Main menu, this window is not a teammate instance, the current character is not auto-playing, **and** the play model is configured, the endpoint is valid and `Test connection` has passed | Only the first three structural conditions; **the model can be left entirely unconfigured** |
| Teammate process | Joins the lobby -> clicks start -> plays cards automatically after entering the map | Joins the lobby -> clicks start -> after entering the map **stays in place**: the child process gets `STS2_AGENT_AUTOPLAY=0`, `/health` reports `play_phase: "paused"` and `session_requests: 0`, and it never plays cards or calls the model |
| Who plays | The model loop in the teammate process | An external agent calls the teammate instance's `GET /state` and `POST /action` itself |
| Start / pause | "Pause teammate / Resume play" in the main window, or `POST /teammate/control` | Same; if a play model is completed and verified afterwards, `running: true` makes the teammate start playing by itself |
| How to tell | `companion.auto_play` in `/health` is `true` | The same field is `false` |

Both routes share the same set of structural conditions, so the split is only at the model, and it is not a bypass: it must not be a teammate instance, the current character must have no running auto-play, and it must be on the main menu; if any one is missing, the teammate cannot be launched.

Under the external takeover route, the teammate's own `POST /action` is always available and acts only on **its own character** (`CompanionActPolicy`; overstepping returns 403 `forbidden_actor`). Once up, the teammate also does not raise an error for lacking a model: this route never calls the model at all.

```powershell
# The teammate can be launched with no model configured; once up it stays in place waiting for takeover
Invoke-RestMethod -Uri 'http://127.0.0.1:8080/action' -Method POST -ContentType 'application/json' `
  -Body '{"action":"invite_ai_teammate"}'

# Find the teammate instance's HTTP API (the port is usually not 8080, trust the response)
(Invoke-RestMethod -Uri 'http://127.0.0.1:8080/health').data.companion

# Start / pause the teammate's auto-play: go through the main window, no teammate session token needed
Invoke-RestMethod -Uri 'http://127.0.0.1:8080/teammate/control' -Method POST -ContentType 'application/json' `
  -Body '{"running":true}'
```

## `POST /teammate/control`

The supported teammate control entry on the main window: an external agent uses it to start / pause the teammate instance of the current team, **without** holding `X-STS2-Companion-Session`. The main window holds that token itself and calls the teammate instance's `POST /companion/control` with it.

- Authentication: loopback only (a non-local source gets 403 `local_only`), and the main window only (409 `not_host` on a `companion` instance). Same level as the other local endpoints; the token is not handed to the caller and does not appear in any response.
- Request body: `{"running": true|false}`, `running` must be a boolean
- Response: `data.phase` is the phase reported by the teammate (`running` / `paused` / `stopping`), `data.play_running` / `data.play_phase` are from the main window's point of view, and `data.companion_auto_play` is the route of the current team
- Failure: returns 409 `teammate_control_failed` (retryable) when no team is formed, the teammate process has exited, the previous control has not finished, or the teammate did not confirm
- `running: true` needs a verified play model, the same gate as the in-game "Resume play" button; when unverified the request fails and the teammate stays paused

```json
{
  "ok": true,
  "request_id": "req_20260913_101500_0001_7",

    "phase": "paused",
    "play_running": false,
    "play_phase": "paused",
    "companion_auto_play": false
  }
}
```

## `GET /strategy` and `POST /strategy`

The strategy surface of the dual-layer decision mode. When enabled, the TypeSafe Jev model executes action by action and the LLM only does strategic planning; these two routes are the entry through which an external planner reads and adjusts the strategy Jev currently follows. The in-game planner and external MCP clients write the same `StrategyStore`, so the two paths are the same experience.

- Authentication: loopback only (a non-local source gets 403 `local_only`), at the same level as the other local control endpoints
- The `GET /strategy` response keeps `data.strategy` (the current strategy: `posture` / `goal` / `instructions` / `option_hints` / `plan_screen` / `plan_round` / `updated_at` / `source`), `data.dual_layer` (the dual-layer switch state of this instance: the host reads the singleplayer switch, the companion reads the multiplayer switch) and `data.jev_configured` (whether Jev's base URL and key are both set); it adds the read-only `data.run_summary` (the same raw state summary as the `run` of `get_run_summary`; `null` without a valid `run_id`), `data.screen` (the current raw state screen name, nullable), `data.recent_jev_decisions` (up to 5 accepted Jev decisions of the same `run_id`, from oldest to newest, with only `id` / `timestamp` / `action` / `confidence`) and `data.confidence_trend` (with `count`, `average`, `latest`, `direction` when there are confidence samples; otherwise `null`). `direction` is `rising` / `falling` / `steady`, and `insufficient_data` for a single sample; the trend is computed over the samples that have `confidence` among at most the 5 recent Jev decisions. With no run the decision list is empty and the previous run is not borrowed. This response is produced by the same C# projection as the native MCP `get_planner_briefing`, and the Python MCP forwards the `data` of `/strategy` directly, without separately reading `/state`/`/decisions` across frames. It contains no reasons, prompts, Jev key or request body.
- `POST /strategy` request body `{"strategy": {...}}` (or the strategy object directly); `posture` / `goal` / `instructions` / `option_hints` are all optional and **omitted fields keep their current value** (the same merge as the native MCP `update_play_strategy`; this route used to reset omitted fields to defaults). An explicitly passed `option_hints` replaces the old table as a whole. `source` is recorded as `mcp` and `updated_at` as the current time. When there is no recognizable, correctly typed field at all (including `{}`) or the body is not an object, it returns 400 `invalid_request` and does not reset the strategy to defaults
- Strategy field conventions: `posture` is the overall tendency (such as `aggressive` / `defensive` / `balanced`); `goal` is a one-sentence macro objective, placed at the very front of every Jev choice and truncated beyond 400 characters; `instructions` is long-term guidance and **must not** name specific card indexes or targets, because they change every frame; `option_hints` are written by **action category** (`play_card`, `end_turn`, `choose_map_node` ...), and the executor maps them to the concrete option IDs of the current frame (such as `play_card:0->1`); keys written as indexes are discarded
- `plan_screen` / `plan_round` are read-only provenance: the in-game planner records on which screen and in which combat turn the strategy was written, and Jev requests use it to mark an old strategy carried over across combats. External writes cannot set them; they are kept when only `posture` changes and cleared when `goal` / `instructions` / `option_hints` are rewritten

## `GET /companion/jev`, `POST /companion/control` and `POST /companion/message`

Controlled endpoints on the AI teammate instance, called locally by the host process and not used by the normal player window.

- Available only on a `companion` instance, over loopback, and when the request header `X-STS2-Companion-Session` matches the session token the instance holds; otherwise it returns 403 `companion_session_required`
- The token is generated when the host launches the teammate process and passed to the teammate through an environment variable; it exists only in the local dual-launch scenario
- `GET /companion/jev`: no request body; the response `data` is a `CompanionJevSnapshot`, containing `choice`, `probabilities`, `danger`, `latency` (nullable text of the Jev panel for the current teammate; empty state when there is no reading yet) and `dual_layer_coop_enabled` (the multiplayer dual-layer switch in force for the current teammate, a boolean). It returns only the teammate instance's readings, and never the API key, the session token, the full settings or a fake reading from a previous instance; this endpoint is not a general public health check and is for the token-holding host to poll only
- `POST /companion/control`: the old request body `{"running": true|false}` is still valid, and the response carries `data.phase`; a teammate that has been remotely paused will not start again on its own. It can also be passed alone as `{"settings": {"dual_layer_coop_enabled": true, "jev_base_url": "...", "jev_api_key": "...", "jev_model": "...", "jev_confidence_threshold": 0.6, "jev_request_timeout_seconds": 90}}`, which syncs only these allowlisted fields to the current teammate and takes effect on the next turn; it must not be passed together with `running`. The response contains only `data.phase` / `data.settings_applied` / `data.dual_layer_coop_enabled` and **never echoes the key**
- `POST /companion/message`: request body `{"message": "..."}` (1-2000 characters), and the response `data.reply` is the teammate's reply

### Typed signal (optional) of `POST /companion/message`

Free text is unreliable for the decision loop: "I'll hit the left one" neither says which `enemy_index` it means, nor can two people saying it twice be told to mean the same one. So besides `message` an **optional** `intent` object can be sent; `message` itself is still required and is still the human-readable part.

| Field | Type | Applies to `type` | Description |
| --- | --- | --- | --- |
| `type` | string | Required | One of `focus_fire`, `target_announce`, `potion_ownership` |
| `enemy_index` | number | `focus_fire` / `target_announce` | Index of the enemy targeted this turn (the `combat.enemies[].i` index set), required |
| `potion_index` | number | `potion_ownership` | Potion slot index, required |
| `player_id` | string | `potion_ownership` | Whose potion this is; when omitted the line is shown as "unspecified player" |
| `potion_id` | string | `potion_ownership` | Potion ID; when omitted it is shown as "a potion" |

- **Backward compatible**: a request without `intent` is exactly as before; `intent: null` is the same as omitting it.
- **A malformed signal is rejected, not dropped**: a missing or unknown `type`, a missing required field for that type, or a wrong field type all give 400 `invalid_request`. Silently dropping a signal would look like the teammate ignoring the instruction.
- **Extra fields are ignored**, so earlier and later versions can coexist.

A received signal enters the teammate's decision context as a separate field (alongside the message text, each answering a different question), and when `focus_fire` / `target_announce` is present it adds a **constraint** to the teammate's next decision: the teammate is attacking `enemy_index N` this turn, so do not pour more damage into it unless that enemy is already certain to die or has only a last hit left. This is a prompt-level constraint, not a hard rewrite of the card plays: the model can see live HP and `lethal_risks` and can tell "do not duplicate" from "finish it off", and rejecting an action in code would take that judgment away.

## `GET /data/{collection}`

Exports game metadata collections for the MCP side to query cards / relics / monsters and so on. Collection names are case-insensitive, and an unknown collection returns 404 `collection_not_found`.

| Collection | Content |
| --- | --- |
| `cards` | Cards: id, name, cost, rarity, type, keywords, tags, dynamic value variables and so on |
| `relics` | Relics: id, name, rarity, description |
| `monsters` | Monsters: id, name, HP range, intents |
| `potions` | Potions: id, name, rarity, target type |
| `events` | Events: id, title, options |
| `powers` | Buffs / debuffs: id, name, type, description |
| `characters` | Characters: id, name, starting deck, starting relics, starting potions |

The export has to read game objects, so it runs on the game thread; the data is large (the card collection is several hundred KB), and it is not suitable to pull on every decision. The MCP side (`sts2_mcp.client.Sts2Client.get_game_data_collection`) caches it in-process.

**The metadata is on the singleplayer scale.** The `min_hp` / `max_hp` of `monsters` are the base HP range the monster rolls, while in a multiplayer run the game scales them by `player count x act factor` (1.1 for act 0, 1.2 for act 1, 1.2 for act 2, and 1.3 for the Boss room of act 2) before they land on the live enemy, so the two often do not match. To align them, look at the live `combat.enemies[].base_max_hp`: it is on the same scale as the metadata, and `max_hp` is the scaled value.

When the MCP-side `get_relevant_game_data` reads this metadata, `item_ids` can be omitted: when omitted, the current screen decides which ids to look up (combat looks at the hand and enemies, the shop at the shelves (cards / relics / potions all use the offer id on the shelf), the card reward at `reward.card_options[]` / the compact view's `reward.cards[]`, the selection screen at `selection.cards[]`, the chest at `chest.relic_options[]` / the compact view's `chest.relics[]`, bundle selection at `bundles[].cards[]`, and an event at the current event), and the fields are trimmed to the subset that scenario needs. Queries are separated by collection: when what the screen offers is cards, asking `relics` does not answer with card ids, and vice versa; the gold / potion / relic rows of the reward screen have no stable id, so none is made up and it goes straight to the fallback. When a screen is classified into a scenario but that scenario's payload has no content on this screen (for example `FAKE_MERCHANT` is classified as shop but has no `shop` payload), or the screen does not offer this collection at all, it falls back to the character-level ids of the deck / relics / potions; when there really are no ids for that collection it returns `{}` and does not make anything up. To ask about a specific id, pass `item_ids` as usual.

### Typical usage

```powershell
Invoke-RestMethod -Uri 'http://127.0.0.1:8080/data/cards' | ConvertTo-Json -Depth 3 -Compress
```

## `GET /decisions`

Returns the **accepted** decisions in chronological order (oldest first, newest last), for reviewing "why was this step played this way". This is one log shared within the process: in-game auto-play, `POST /action` (external agents) and the native MCP `act` all write the same one, and `source` tells the origin apart.

The query parameter `limit` is optional, default 50, maximum 200; an out-of-range value is clamped to the boundary, and an invalid value falls back to the default.

| Field | Type | Description |
| --- | --- | --- |
| `id` | number | Monotonically increasing sequence number within the process, starting at 1 |
| `timestamp` | string | ISO 8601 UTC timestamp |
| `source` | string | The writer: `agent_loop` (the LLM decision of in-game auto-play), `jev` (the decision of the Jev executor model in dual-layer mode, with `confidence`), `http_api` (`POST /action`), `native_mcp` (the native MCP `act`) |
| `action` | string | Name of the accepted action |
| `reason` | string \| null | The one-sentence reason the action carries; `null` when the caller gave none |
| `state_fingerprint` | string \| null | Compact state fingerprint after the action executed (used by the no-progress guard); `null` when unavailable |
| `requests_spent` | number | Model requests spent on this step (`http_api` / `native_mcp` record 0) |
| `total_tokens` | number \| null | Total tokens of this step; `null` when the model did not report usage |
| `run_id` | string \| null | Which run this step belongs to; `null` when no run has been recognized yet (the Mod's internal placeholder `run_unknown` is never written in, otherwise it would mix all pre-run decisions into one bucket) |
| `confidence` | number \| null | `jev` rows only: Jev's confidence in the chosen action (0-1); a choice below the threshold is not executed and so never appears in the log; other sources have no such value (the field is omitted or `null`) |
| `option_ids` | string[] \| null | Dual-layer turns only: all option IDs enumerated to Jev in that frame (in frame order, capped at 48). Used to review afterwards "could that card really be played at the time", and the consecutive `end_turn` of 2026-09-23 could not be characterized for lack of this evidence |
| `probabilities` | object \| null | `jev` rows only: the per-option probability distribution Jev reported (keys are option IDs) |
| `danger` | number \| null | `jev` rows only: Jev's danger score for the current frame (0-4) |
| `strategy_updated_at` | string \| null | Dual-layer turns only: the `updated_at` timestamp of the strategy the decision was based on, to tell "which version of the plan this step used" |
| `jev_attempt` | boolean \| null | Appears only on `agent_loop` rows and when `true`: this step is an LLM fallback after Jev failed to submit (Jev already spent a request); omitted on ordinary LLM decision rows |

Only **accepted** actions enter the log: an action name not in `available_actions`, an out-of-range index or a failed execution is not recorded, so the log never contains a choice that never happened on the player's screen.

The reason text comes from the model's `reason` parameter (see `client_context.decision_reason` of `POST /action`), and before it is written to disk it goes through the same redaction and length trimming as the diagnostics export.

The log is also appended as JSONL to `decisions.jsonl` in the same directory as the settings file (default `%APPDATA%\STS2AIAgent\decisions.jsonl`), and rotates to `decisions.jsonl.previous` beyond 2 MB. Writing to disk is best effort: when the diagnostics directory is not writable it only affects the disk write, not the run.

`run_id` is for "how much did this run cost": one auto-play session can span more than one run, so the session total and the run total answer two different questions. The overlay's "Decision log" page shows both lines; when the model did not report usage, this run's tokens are shown as **unknown** rather than 0, because "nothing spent" and "nobody told us" are not the same thing.

### Response example

```json
{
  "ok": true,
  "request_id": "…",
  "data": []
}
```

## `POST /mcp` (native MCP)

The in-process MCP endpoint, at the path `/mcp` (`/mcp/` is equivalent, and route matching is case-insensitive). This is a **separate surface** of MCP Streamable HTTP: `OPTIONS` returns 204, `DELETE` clears the MCP session and returns `{ok:true}`, JSON-RPC is accepted only over `POST`; `GET` and other methods return 405 `method_not_allowed`. It shares the same HTTP listening port with the other routes, by default `http://127.0.0.1:8080/mcp`.

- It must be enabled by ticking it on the in-game overlay's "Connect" page (`mcpEnabled` in settings); when not enabled it returns 403 `mcp_disabled`
- It follows MCP Streamable HTTP semantics: the request body is JSON-RPC, and the response is JSON or SSE
- **Origin policy**: a request with an `Origin` header must match the endpoint authority (a `Host` header may also be sent and must likewise match), otherwise 403 `origin_not_allowed`. A request without `Origin` is let through (native clients). `Origin: null` is always rejected
- This endpoint uses its own error envelope (`{ok:false, error:{code,message}}`) and JSON-RPC error codes, and does not apply the `request_id` envelope of the other routes in this document


### Native MCP tool surface

`/mcp` and the Python sidecar are **two implementations of one tool surface** (the reasons are in ADR 0002): tool names and parameter names are compared in both directions by
`mcp_server/tests/test_native_tool_alignment.py`, the exemption table is empty, and both sides must agree.

| Tool | Purpose |
| --- | --- |
| `health_check` | Whether the Mod is loaded and whether the endpoint is on |
| `get_game_state` | The compact `agent_view` (the default state read) |
| `get_raw_game_state` | The full `/state` |
| `get_available_actions` | Action descriptors (`requires_index` / `requires_target` / target hints) |
| `decide` | Gives `state`, `available_actions` and `scene_guidance` together from **one state read** |
| `get_scene_guidance` | The strategy and playbook paragraphs for the current screen |
| `get_decision_log` / `get_run_summary` / `diff_state` | Decision log / summary of this round / state diff |
| `get_game_data_item` / `get_game_data_items` / `get_relevant_game_data` | Game metadata queries |
| `wait_until_actionable` | Waits until actionable again, then returns the compact `agent_view` (the full `/state` when `raw_state: true`) |
| `act` | The unified action entry |
| `run_console_command` / `inject_event_churn` | Registered only when `STS2_ENABLE_DEBUG_ACTIONS=1` |

The Python sidecar additionally has `wait_for_event` (a convenience tool for the event stream), which the native surface does not include; this is the only explicitly allowed difference in the comparison between the two sides.

`decide` and `get_scene_guidance` each do only one state read: the sidecar's `decide` reads `GET /decision-snapshot`, one game-thread
state build that yields both the compact state and the action descriptors; `get_scene_guidance` reads one `GET /state`. The `available_actions` of `/state`
and the descriptors of `/actions/available` already came from the same walk (ADR 0001), and `/decision-snapshot` makes the two halves share even the frame, so the caller
no longer indexes the state of another frame with one set of action descriptors. `act` also reuses the same snapshot for the legality check and index validation, and no longer builds a state each time.

When an old mod has no `/decision-snapshot` it answers with 404 `not_found`, and `decide` falls back to two calls, "read `/state` + read
`/actions/available`", for this one case only; other errors are raised as usual and are not masked by the second read.

### The result contract of `act`

The `state` of `act` is **the compact `agent_view` of the state after the action** (the same shape as `get_game_state`), not the full
`/state`: most of the latter's fields are renamed in compact (see "compact field rename table"), and it costs about 4,000-9,500 tokens each time.
The other keys such as `action`, `status`, `stable` and `message` are kept unchanged.

- Pass `raw_state: true` (default `false`) when the full payload is needed: `state` is then the `data.state` returned by `POST /action`.
- When the Mod does not expose `agent_view` it falls back to the full payload, which means the same as `compact_agent_view: false` of `get_game_state`.
- With `status: "pending"` (or `stable: false`) do not resend the same action immediately: wait first according to the screen flow returned.
- The `state` of `wait_until_actionable` has the same shape as that of `act` / `get_game_state` (compact, with the `compact_agent_view` marker),
  and likewise supports `raw_state: true`; the wait happens during animations and transitions, exactly when the full payload is least needed.
- `status: "outcome_unknown"` (unique to the Python sidecar, see `mcp_server/README.md`): the action request may have been executed but the response was lost.
  The client does **one** `/state` reconciliation only and puts the state it read in `reconciliation.state` (compact, with the marker);
  `reconciliation` uses `state_read` / `action_effect_compared` / `action_outcome` to say "the state was read, but the action's effect was never compared against it, and the outcome is still unknown",
  and the top-level `succeeded` / `status` describe that read rather than the action itself. **Never replay the action automatically.**

### Uniform shape of tool errors

The failure content of `tools/call` (`isError: true`) is a piece of JSON text, whose `error` has the same shape as the HTTP routes:

```json
{
  "error": {
    "code": "invalid_target",
    "message": "card_index 9 is not in the latest combat.hand.",
    "details": {
      "action": "play_card",
      "field": "card_index",
      "submitted": 9,
      "valid_field": "combat.hand",
      "valid_indices": [0, 1, 2],
      "locked": false,
      "available_actions": ["end_turn", "play_card"]
    },
    "retryable": false,
    "status_code": 409
  }
}
```

- Index-type rejections (`invalid_request` / `invalid_target`) give in `details` the `field` (the field in error),
  `submitted` (the submitted value), `valid_field` (the path of that index in the compact state) and `valid_indices`
  (the indexes the payload really accepts at the moment), so the model can correct directly instead of resending the same index.
- The human-readable text is unchanged and is still in `error.message` (the example above is the original string).
- The exception path likewise gives `code` / `message` / `details` / `retryable`; `status_code` appears only when it is an
  `ApiException` and is otherwise omitted. The Python sidecar side keeps the same keys: the Mod's HTTP `error.details`
  is kept unchanged, with `field` / `submitted` / `valid_indices` added (derived from counts such as `hand_count`
  and `option_count`).

### Result contract of `get_scene_guidance` and `decide.scene_guidance`

Both surfaces answer with these four shared keys (the `scene_guidance` in `decide` is the same as the return value of `get_scene_guidance`):

| Key | Type | Description |
| --- | --- | --- |
| `screen` | string \| null | `state.screen`; `null` when unavailable |
| `scene` | string | The metadata scene `screen` maps to: `combat` / `shop` / `event` / `reward` / `card_selection` / `chest` / `bundle_selection` / `menu` (`menu` is the fallback for the remaining screens) |
| `guidance` | string | The strategy paragraph for that screen. For a screen with no strategy choice (such as the reward screen) it is an empty string, which is an answer and not a failure |
| `playbook` | string | The operating-procedure paragraph for that screen, **never empty**: a screen that maps to no chapter gets the chapter index, to avoid treating "no content" as "nothing to know" |

The Python sidecar adds `event_id`, `event_options` and `guidance_source`: they come from the repository's offline event risk
index (`docs/game-knowledge/events.md`), which the Mod does not carry, so the native surface answers only the four shared keys above.

`event_id` returns `state.event.event_id` unchanged (such as `NEOW`), without rewriting. The lookup uses its canonical form
`canonical_event_id`: the same algorithm as `StringHelper.Slugify`, so the live `NEOW` and the class name `Neow` in the table
land on the same key. Each row of `event_options` is a row of the table, and the `option` field is the in-page key with the `<EVENT>.pages.` prefix **removed**
(`INITIAL.options.ARCANE_SCROLL`); remove the same prefix from the live `text_key` and it pairs with it verbatim.
The match does only case normalization and this one prefix strip, with no prefix / substring / similarity matching, so two events with similar names in the two tables
are not merged; an id not in the table returns an empty array, not the closest row.


## Implemented action details

### `end_turn`

Ends the current combat turn.

- **Precondition**: `screen = "COMBAT"`, in the player's card-play phase
- **Parameters**: none
- **Stable condition**: the turn number changes, or it is no longer the player phase, or combat has ended
- **Timeout**: 5 seconds

```
Request: { "action": "end_turn" }
```

```json
{
  "ok": true,
  "request_id": "req_20260310_120010_0001",
  "data": {
    "action": "end_turn",
    "status": "completed",
    "stable": true,
    "message": "Action completed.",
    "state": { "screen": "COMBAT", "turn": 2, "..." : "..." }
  }
}
```

### `play_card`

Plays one card from the current hand.

- **Precondition**: `screen = "COMBAT"`, and the hand has a card with `playable = true`
- **Parameters**:
  - `card_index` (required): index into `combat.hand[]`
  - `target_index` (conditionally required): when the card has `requires_target = true`, the index into `combat.enemies[]`
- **Stable condition**: the card has left the hand and the player-driven action queue has drained
- **Timeout**: 5 seconds

```json
{
  "action": "play_card",
  "card_index": 0,
  "target_index": 0
}
```

**Error scenarios**:

| Scenario | Error code | Description |
| --- | --- | --- |
| Missing `card_index` | `invalid_request` | "play_card requires card_index." |
| `card_index` out of range | `invalid_target` | "card_index is out of range." |
| The card needs a target but `target_index` was not passed | `invalid_target` | "This card requires target_index." |
| `target_index` out of range | `invalid_target` | "target_index is out of range." |
| The card cannot be played | `invalid_action` | "Card cannot be played in the current state." |

### `choose_map_node`

Chooses a node to travel to on the map screen.

- **Precondition**: `screen = "MAP"`, and `map.available_nodes` is non-empty
- **Parameters**: `option_index` (required): index into `map.available_nodes[]`
- **Stable condition**: the room has been entered, or the map coordinates changed, or the screen switched
- **Timeout**: 10 seconds

Route planning should be based on the parent-child links of the full graph in `map.nodes[]`; `map.available_nodes[]` is only for executing the current step.

```json
{
  "action": "choose_map_node",
  "option_index": 0
}
```

### `resolve_rewards`

Advances the whole reward flow in one call: claims each claimable reward one by one, handles any card reward selection it meets, and finally clicks continue.

- **Precondition**: `screen = "REWARD"` (`reward.rewards[]` has claimable items, or it is already on the card reward sub-screen)
- **Parameters** (both can be omitted)
  - `option_index`: `-1` skips the card reward; `0/1/2...` chooses the card at that position (the index refers to `reward.card_options[]`); **when omitted, a card is no longer picked automatically**: on meeting a card selection it stops and returns `pending`, and the caller decides
  - `card_index`: a backward-compatible alias of `option_index`, with the same meaning
- **Behavior**: shares the same reward advance flow as `collect_rewards_and_proceed`; an explicit choice applies only to the first card reward selection met in this call. When no choice is carried, the flow stops on the card selection screen (`reward.pending_card_choice = true`) and returns `pending`: a card is a deckbuilding decision, and the Mod no longer takes the first one on the caller's behalf
- **Stable condition**: the reward flow ends, the screen switches, or it stops on the card selection screen to wait for a decision
- **Timeout**: 20 seconds
- **Retry semantics**: an explicit choice belongs to **the call that carries it**. If this call returns `pending`, retrying `resolve_rewards` with the same parameters carries the choice again; retrying without a choice (or switching to `collect_rewards_and_proceed`) stops at the card selection again and does not pick a card automatically

```json
{
  "action": "resolve_rewards",
  "option_index": 1
}
```

### `claim_reward`

> Note (`2026-03-11`): when the claimed reward is a card reward, `skip_reward_cards` only closes the current card-selection overlay. The underlying reward may still remain in `reward.rewards[]`, so callers should always re-read state after skipping.

Claims one reward on the main reward screen.

- **Precondition**: `screen = "REWARD"`, and `reward.rewards[]` has an item with `claimable = true`
- **Parameters**: `option_index` (required): index of a claimable item in `reward.rewards[]`

- **Stable condition**: the number of reward buttons changes, or the screen switches
- **Timeout**: 10 seconds

```json
  "option_index": 1
```
```json
}
```

### `skip_reward_cards`

> Note (`2026-03-11`): this action dismisses the current card-reward selection overlay. It does not guarantee that the underlying reward is consumed. After calling it, inspect `reward.rewards[]` and `reward.can_proceed` again.

Skips taking a card on the card reward sub-screen.

- **Precondition**: `screen = "REWARD"`, `reward.pending_card_choice = true`, and `reward.alternatives[]` is non-empty
- **Parameters**: none
- **Behavior**: clicks the first alternative button (usually "Skip")
- **Skip scope**: the skip intent is bound to the reward set that recorded it (the same reward screen instance) and does not affect the card rewards of other reward sets later; if the owning reward set cannot be resolved, the intent does not take effect: better not to skip (the card selection screen reappears, which is recoverable) than to silently discard a reward
- **Timeout**: 10 seconds

### `collect_rewards_and_proceed`

Automatically collects all rewards and clicks continue.

- **Precondition**: `screen = "REWARD"`
- **Parameters**: none
- **Behavior**:
  1. Claims each claimable reward one by one (skipping potions with no free slot)
  2. On meeting a card selection it **stops and returns `pending`** (`reward.pending_card_choice = true`), and the caller decides with `choose_reward_card` / `skip_reward_cards`; it no longer picks the first card automatically
  3. When there is no card decision pending, it clicks the continue button
- **Timeout**: 20 seconds
- **Note**: suited to unattended advancing of non-card rewards. A card selection is a deckbuilding decision and must be made explicitly with `choose_reward_card` / `skip_reward_cards` or with `resolve_rewards` carrying `option_index`

```
Request: { "action": "collect_rewards_and_proceed" }
```

### `select_deck_card`

Chooses one card on the card selection screen. Every click on the deck grid settles and returns `completed`; a multi-select in the combat hand only accumulates the current step and returns `pending`, and `confirm_selection` is needed to finish it.

- **Precondition**: `screen = "CARD_SELECTION"`, and `selection.cards[]` is non-empty
- **Parameters**: `option_index` (required): index into `selection.cards[]`
- **Behavior**: two cases by `selection.kind`
  - Deck grid (`deck_card_select`, `deck_upgrade_select`, `deck_transform_select`, `deck_enchant_select`, `choose_card_select`): returns `completed` once the native screen confirms the click. **This does not mean the screen has closed**: when `min_select < max_select` the screen stays open and keeps collecting, so read `selection.selected_count` / `max_select` to decide whether to keep clicking; when full, or when you want to finish early, finish with `confirm_selection` (see below)
  - Combat hand multi-select (`combat_hand_select`, `combat_hand_upgrade_select`): only counts this step and returns `pending`, and the screen stays open. Read `selection.selected_count` / `max_select` / `requires_confirmation` to judge whether more choices are needed, and finish with `confirm_selection`
  - Verified on a real game: card removal, upgrade (single select), enchant (0/3, multi-select), transform (0/6, multi-select), event multi-select (2/2). For screens with `min_select < max_select` such as enchant / transform, each click returns within about 0.15 seconds and no longer spins until a timeout
- **Stable condition**: the click on the deck grid is accepted by the native screen (`selected_count` changes); a combat hand multi-select leaves the selection screen after `confirm_selection`
- **Timeout**: 10 seconds

```json
{
  "action": "select_deck_card",
  "option_index": 0
}
```

### `confirm_selection`

Finishes a selection that needs confirmation. One call runs the whole native flow: when needed it first clicks the screen's confirm button to open the preview, then clicks the confirm in the preview.

- **Precondition**: `selection.can_confirm = true` (it appears in available_actions only when the native confirm button is usable)
- **Parameters**: none
- **Behavior**: the `min_select < max_select` cases of the deck grid (enchant, transform, and reward card selection where `min_select` is 0) and the combat hand multi-select all finish with it. When `max_select` is filled, `select_deck_card` usually finishes by itself, so it is mainly for **finishing early**
- **Stable condition**: leaves the selection screen
- **Timeout**: 10 seconds. Verified on a real game: enchant (0/3) and transform (0/6) both complete within one call (about 0.17-0.19 seconds), with no second call needed

## Typical call flows

### Combat turn

```
1. GET /state                          → get the hand, enemies, energy
2. Choose a playable card (playable=true)
3. POST /action { play_card, card_index, target_index? }  → play the card
4. Repeat 1-3 until no card can be played or you decide to end
5. POST /action { end_turn }           → end the turn
6. Repeat 1-5 until combat ends
```

### Combat settlement → map advance

```
1. GET /state                          → screen=REWARD
2a. POST /action { collect_rewards_and_proceed }  → collect non-card rewards; if there is a card selection it stops on the selection screen (pending_card_choice=true)
    POST /action { choose_reward_card, option_index=2 }  → pick a card by deckbuilding decision (or skip with skip_reward_cards)
--- or ---
2b. POST /action { claim_reward, option_index=0 }  → claim the gold manually
    POST /action { claim_reward, option_index=1 }  → click the card reward
    GET /state                                     → confirm pending_card_choice=true
    POST /action { choose_reward_card, option_index=2 }  → pick a card
    POST /action { proceed }                       → continue (if there is a button)
3. GET /state                          → screen=MAP
4. POST /action { choose_map_node, option_index=0 }  → choose a route
```

### Chest room

```
1. GET /state                          → screen=CHEST, chest.is_opened=false
2. POST /action { open_chest }         → open the chest, wait for the relics to be shown
3. GET /state                          → chest.relic_options[] lists the selectable relics
4. POST /action { choose_treasure_relic, option_index=0 }  → choose a relic
5. GET /state                          → chest.has_relic_been_claimed=true
6. POST /action { proceed }            → continue to the map
```

### Event room

```
1. GET /state                          → screen=EVENT, event.options[] lists the selectable options
2. Choose an option with is_locked=false
3. POST /action { choose_event_option, option_index=0 }  → choose the option
4. GET /state                          → the event may update its options or complete
5. If event.is_finished=true, the only option left is proceed (index=0)
6. POST /action { choose_event_option, option_index=0 }  → leave the event, return to the map
```

### Crystal sphere divination

```
1. GET /state                          → screen=CRYSTAL_SPHERE
2. Read crystal_sphere.items / hidden_cells and plan coordinates that avoid completely revealing known (**revealed**) bad items
   (for unrevealed items `kind` / `is_good` are `null`, so plan by footprint only)
3. POST /action { crystal_clear_cell, x, y, tool="big" }
4. Repeat 1-3 until divinations_left=0
5. Handle any reward sub-screen that may appear; after returning to the divination screen, POST /action { proceed }
```

### Rest site (restore HP)

```
1. GET /state                          → screen=REST, rest.options[] lists the selectable actions
2. Choose the HEAL option with is_enabled=true
3. POST /action { choose_rest_option, option_index=0 }  → restore HP
4. GET /state                          → ProceedButton is available
5. POST /action { proceed }            → continue to the map
```

### Rest site (upgrade a card)

```
1. GET /state                          → screen=REST, rest.options[] lists the selectable actions
2. Choose the SMITH option (is_enabled=true means there is an upgradable card)
3. POST /action { choose_rest_option, option_index=N }  → enter card selection
4. GET /state                          → screen=CARD_SELECTION, selection.cards[]
5. POST /action { select_deck_card, option_index=M }    → choose the card to upgrade
6. GET /state                          → back at REST, ProceedButton is available
7. POST /action { proceed }            → continue to the map
```

### Shop (buy items)

```
1. GET /state                          → screen=SHOP, shop.is_open=false
2. POST /action { open_shop_inventory } → open the inventory panel
3. GET /state                          → shop.cards[] / shop.relics[] / shop.potions[]
4. POST /action { buy_card, option_index=0 } or buy_relic / buy_potion
5. GET /state                          → gold and inventory updated
6. POST /action { close_shop_inventory } → close the inventory
7. POST /action { proceed }            → leave the shop, return to the map
```

### Shop (remove a card)

```
1. GET /state                          → screen=SHOP, shop.card_removal.available=true
2. POST /action { open_shop_inventory } → open the inventory panel
3. POST /action { remove_card_at_shop } → enter CARD_SELECTION
4. GET /state                          → screen=CARD_SELECTION, selection.cards[]
5. POST /action { select_deck_card, option_index=M } → choose the card to remove
6. GET /state                          → return to SHOP or you can leave
7. POST /action { proceed }            → return to the map
```

### Debug actions

`run_console_command` and `inject_event_churn` are for development-time debugging / verification only, and are off by default.

- How to enable: set the environment variable `STS2_ENABLE_DEBUG_ACTIONS=1`
- Release advice: do not enable them in the default configuration of an official release
- Design goal: to speed up local real-game verification; they should not become a routine dependency of a production play agent

`inject_event_churn` is dedicated to verifying the slow-subscriber contract of `/events/stream`: it publishes N `debug_churn`
synthetic events through exactly the same publishing path as all other events. The typical usage is to open one stream that **does not read** and another that reads normally,
then `POST {"action":"inject_event_churn","option_index":400}`: the non-reading one gets its
256-slot queue filled and is **closed by the server**, the normal one keeps receiving events, and the game log shows
`Disconnected 1 slow event subscriber(s)`. Before this the path had only offline evidence, because a real game cannot naturally produce
256 state changes (polling publishes only when a field really changes). The `count` upper bound is 5000, and anything below 257 is rejected, with the reason written in
`EventChurnPolicy`: a request that cannot fill a queue proves nothing.
