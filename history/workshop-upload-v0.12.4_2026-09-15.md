## Changes in This Upload (relative to v0.12.3 on the Workshop)

See the v0.12.4 section of [CHANGELOG.md](../CHANGELOG.md). The two that players notice directly:

1. Inviting / continuing the teammate returns `pending` immediately, so a slow launch no longer looks like a client timeout; while a dual-instance launch is in progress these two actions no longer appear in the available actions, and a second request can no longer report the previous round's success as its own result.
2. Request accounting is accurate: every model call that was actually sent is booked (chat and proactive speech failures and unexpected exceptions in the tool loop are no longer missed), so the request limit on the play page matches the actual spend.

## Process Notes (to reuse next time)

1. **This time it got stuck twice in a row at `Upload starting` with no progress at all**: 10 minutes at 19:21 and 4 minutes at 19:31; the Steam-side `workshop_log.txt` neither reported an error nor entered `k_EItemUpdateStatusPreparingContent`; `%LOCALAPPDATA%/sts2-mod-uploader/win-x64/mod-uploader.log` is written only at the end, so the stages cannot be seen in the meantime.
2. **The fix is to restart the Steam client**: `steam.exe -shutdown` -> wait for the `steam` process to exit -> relaunch -> wait for `RecvMsgClientLogOnResponse() : ... 'OK'` to appear in `connection_log.txt`, then rerun the same upload command; within 10 seconds it went through UploadingContent -> UploadingPreviewFile -> CommittingChanges and succeeded.
3. The upload command is `& ModUploader.exe upload -w <workspace> -i 3796486050`, with `HTTP_PROXY` / `HTTPS_PROXY=http://127.0.0.1:10808` in the process environment. Proxy availability can be self-checked first: `curl -x http://127.0.0.1:10808 https://steamcommunity.com/` returned 200 this time, showing the stall was unrelated to the proxy.
4. The `k_EItemUpdateStatusInvalid` at the tail is the terminal value of the SDK status enum, and `Successfully uploaded` is still printed afterward, so it does not indicate failure; this matches the historical success records.

## 2026-09-15 / 16 Two Same-Number Re-releases (Second and Third Uploads)

On the same day `0.12.4` was re-cut twice, and the three builds share one version string.

### Second Upload (Abandoned, Lived About an Hour)

Fix: a one-frame race in which `available_actions` and `combat.action_readiness` contradicted each other within a single `/state` response:
the combat gate was evaluated several times in one payload, and when it straddled the 200ms stability sampling window the first half judged "unstable" and the second half judged "stable".
