## Contents

The theme of v0.14 is **decisions that explain themselves + deeper two-player cooperation**:

- **Decision explanation chain**: an action can carry a reason, and `AgentTurnResult.Reasoning` is no longer empty for non-thinking models. The reason goes into
  the overlay's "Decision log" page, `GET /decisions`, `get_decision_log` on both MCP surfaces, and the new SSE event
  `decision_made`. Decision entries carry `run_id`, so spend can be summed per run; when the model does not report usage it shows "unknown" instead of 0.
- **Strategy layer**: new rules for route / rest site / shop / potion timing / combat priority / two-player division of labor, injected per screen
  (`skills/sts2-mcp-player/references/strategy.md` + `PlaybookSections`). The new MCP tool
  `get_scene_guidance` returns the current screen's strategy in one call, and event screens come with per-option risk grading.
- **Knowledge base**: the card table gained Owner and a readable Effect; the event table gained per-option handler / cost / risk (77 -> 357 rows).
- **Cooperation**: `POST /companion/message` supports an optional structured `intent` (`focus_fire` / `target_announce` /
  `potion_ownership`), and a malformed one returns 400 instead of being silently dropped; the host panel shows the teammate character's live HP /
  block / energy / hand size.
- **UI redesign**: a new design system (spacing and type scales, sectioned cards, primary/secondary button hierarchy, a highlighted-pill current tab) and
  four color themes (Dusk / Midnight / Parchment / High contrast), selectable in settings and effective on save; each theme is bound by an offline contrast
  floor.
- **Machine-readable API**: `docs/openapi.json` (OpenAPI 3.1, 12 paths / 76 schemas) is generated by `scripts/api_schema.py`,
  and the 12th release gate compares it byte for byte.
- **New MCP tools**: `get_run_summary` and `diff_state` (added on both surfaces).
- **Model compatibility**: `max_tokens` / `max_completion_tokens` is retried once based on the server error; a 400 for an over-long context
  is not misjudged.
- **Event stream** (v0.13.1, originally planned as its own release, was folded into this one): SSE polling is demand-driven, slow subscribers are explicitly disconnected,
  shutdown does not resurrect event state, and the `inject_event_churn` debug action was added.
- **Validation tooling**: `run_sts2_validation.py patch-check` runs the patch regression in a single command;
  `scripts/test-isolated-settings.ps1` pins isolated-profile seeding.
- **Code health**: `GameStateService.cs` 5,037 -> 1,336 lines (split into 8 per-screen partials, with 218 declaration-level
  SHA-256 proofs of byte-for-byte relocation).

## Workshop Upload Process (with Root Cause)

The upload on 2026-09-21 failed repeatedly at first, and the root cause finally located was **neither the uploader nor Steam being offline**, but
**this machine's system proxy standing in the way of Steam's content delivery (SteamPipe) path**. The process:

1. The first attempt stalled at `k_EItemUpdateStatusPreparingConfig`: `steam-workshop/README.md` recorded this
   symptom (and treated "restart the Steam client" as the remedy at the time).
2. After restarting Steam and retrying, the symptom moved forward to `k_EItemUpdateStatusPreparingContent`, with no progress after a few minutes; the next attempt
   returned `k_EItemUpdateStatusInvalid` / `k_EResultFail` directly.
3. Checking `connection_log.txt` showed the Steam client was **offline** at the time (all `*.steamserver.net` connection manager
   connections timed out, `StartAutoReconnect() attempt 5/6`), and only the ordinary HTTP
   connectivity test through the proxy `127.0.0.1:10808` was OK. An upload needs a live Steam connection, so this step was bound to fail. After Steam
   `Logged On` again at 09:56:30, `workshop_log.txt` could record `Upload starting ...`, but **the manifest stage still stalled**.
4. 6 consecutive attempts (6 minutes each) all stopped at `PreparingContent` and never reached `UploadingContent`.
5. **The root cause was confirmed after changing method**: the system proxy was temporarily turned off (`ProxyEnable=0`) and Steam was restarted; Steam still
   `Logged On` (showing its connection managers connect directly and do not depend on the proxy), and then running the same uploader again
   **finished in 8 seconds**, with `workshop_log.txt` recording `[2026-09-21 10:44:21] Upload finished for workshop item
   3796486050 : OK`. The system proxy was afterwards restored to its original value (`ProxyEnable=1`, `127.0.0.1:10808`).

**Conclusion: the proxy is a known obstacle to uploading to the Workshop from this machine.** It does not affect Steam login or Steam Web API queries,
and only hangs SteamPipe's content transfer. Before the next upload, turning the proxy off and restarting Steam is far more effective than retrying repeatedly;
this has been written into [steam-workshop/README.md](../steam-workshop/README.md), replacing the earlier "a restart fixes it".
