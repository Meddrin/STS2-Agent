## A defect found and fixed: the first-boot seed regressed when "the template was already ready"

**Symptom**: after launching with a brand-new clientId `2026091502` (and later a hand-made `2026091503`) the mod was not loaded at all and `/health` refused connections;
the settings.save written to disk was 3297 bytes, `mods_enabled` was lost, and only one mod record remained: the game clearly did not accept that seed file.

**Root cause**: both the readiness check and the repair on the PowerShell side used a fixed +/-200 character window around `"id": "STS2AIAgent"`. In the mod list of the Steam template,
the AI teammate entry is immediately followed by `DamageMeter`, whose `is_enabled` is `false` and falls right into the window, so:

1. A **fully usable** template clone was judged "not ready" (`ready_before=False`, measured);
2. The repair flow was triggered, and its flip regex used the same window and changed the **next mod's** `is_enabled: false` to `true`;
3. The repaired text still failed the check -> a 788-byte minimal fallback was written;
4. The game did not accept that minimal file, rewrote it to defaults at startup and dropped `mods_enabled` -> the mod did not load.

**Fix**: added `Get-IsolatedAgentEntryBody` (locating the AI teammate's own object by brace matching); both the readiness check and the `is_enabled` flip are performed only inside
that object; `scripts/start-game-session.ps1`. After the fix the same template gives `ready_before=True` (no repair needed), and a brand-new clientId gets a complete clone.
Regression tests: `mcp_server/tests/test_posix_script_portability.py` gains 2 (the entry function exists and is called in two places; no more fixed-character-window checks of `is_enabled`).

## A defect fixed: self-contradictory single-frame state (fix in the 0.12.4 same-number re-release)

Automated sampling caught 1 case among 146 combat snapshots (1 of 36 samples that were `ready` with playable cards in hand):
within the same `/state` response, `combat.action_readiness` says `can_use_combat_actions=true` (`reason=ready`, `snapshot_stable=true`,
`hand_mode=Play`), and both cards in hand are `playable=true` / `can_play_result=true`, but `available_actions` has only
`discard_potion` / `use_potion`: no `play_card`, and no `end_turn`.
The full snapshot is saved at `%TEMP%/sts2_mismatch_dump.json` (captured on the spot, not inferred).

Reading (corrected 2026-09-15): earlier reading the dump's top-level `"energy": null` as "`combat.energy` is null, the combat payload was only half filled" was **wrong**:
`CombatPayload` never had a top-level `energy` field (energy is at `combat.player.energy`), and that `null` was a probe field the capture script wrote into the dump itself,
constituting no evidence. The real root cause is that **the combat gate was evaluated multiple times within the same response**: `BuildAvailableActionNames` (end_turn -> play_card -> ... -> potions)
and the readiness in the subsequent `BuildCombatPayload` each independently called `CanUseCombatActions`, and the stability sampler inside has a 200ms window that resets when the signature changes.
When a response straddles that window, the first half judges "not stable" and gives no `play_card`/`end_turn`, while the second half's potions and readiness judge "stable": the same response contradicts itself.
Impact: a poller may see one frame without a card-play entry (recovered at the next poll); if `state-invariants` happens to sample that frame it reports
`missing action 'play_card'`; none of this round's invariant calls hit it, with 0 failures on both sides.

Fix (0.12.4 same-number re-release): `BuildStatePayload` now evaluates `CombatActionGate` only once and passes the same result to
`BuildAvailableActionNames`, `BuildCombatPayload`, and `BuildRunPayload`; `combat.action_readiness` becomes a pure projection of that gate,
the read-only `IsCombatActionSnapshotCurrentlyStable` was deleted (it was exactly the half that could "change its tune" within one response), and the gate also adds the two locks `modal_open` and `combat_paused`
that were previously checked only in readiness. For the contract tests see `STS2AIAgent.Tests/GameStateCombatGateContractTests.cs`.
